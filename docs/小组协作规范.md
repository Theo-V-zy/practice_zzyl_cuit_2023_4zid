# 小组协作规范

## 分支规则

- `main`：稳定主分支，只放已经能运行的代码。
- `dev`：日常联调分支，所有功能先合并到这里测试。
- `feature/<负责人>-<功能组>`：个人开发分支，例如 `feature/member-a-resident-flow`。
- 合并方式：每个人开发完成后提交 Pull Request，由组长检查后合并。

## 每天开发流程

```bash
git checkout dev
git pull
git checkout 自己负责的feature分支
```

开发完成后：

```bash
git add .
git commit -m "完成护理项目查询"
git push -u origin feature/你的模块名
```

## 提交要求

- 每次提交只做一类事情，例如“新增接口”“修复页面样式”“补充 SQL”。
- 提交前至少确认前端能打开、后端能启动。
- 改数据库结构时，同步修改 `database/zzyl.sql`，并在 PR 里说明。
- 不直接改别人的模块，确实需要改时先在群里说一声。

## 推荐分工

## 功能分工

| 负责人 | 管理端功能 | 家属端功能 | 建议分支 |
| --- | --- | --- | --- |
| 组长 | 登录、工作台、个人中心、消息中心、权限配置 | 登录、我的 | `feature/leader-base-auth` |
| 组员 A | 来访管理、入退管理、在住管理 | 首页 | `feature/member-a-resident-flow` |
| 组员 B | 服务管理、订单管理、财务管理 | 服务 | `feature/member-b-service-order` |
| 组员 C | 客户管理、协同工作、智能监测 | 家人 | `feature/member-c-customer-monitor` |

## 分工说明

- 组长负责基础框架、登录态、权限菜单、个人中心和消息中心，方便最后统一菜单、路由、接口权限和页面风格。
- 组员 A 负责从来访到入住、退住、在住老人管理的完整入住业务链路。
- 组员 B 负责服务项目、服务订单和财务结算，三者数据关系比较紧，放在同一个人手里更好联调。
- 组员 C 负责客户资料、跨岗位协同和智能设备监测，偏信息维护和状态跟踪。
- 家属端按入口分配：组长做登录和“我的”，组员分别做首页、服务、家人，最后统一接入同一套路由和接口。

## Pull Request 规则

- 所有 `feature/*` 分支只向 `dev` 提 Pull Request。
- `dev` 测试通过后，再由组长把 `dev` 合并到 `main`。
- 如果修改了公共接口、菜单、路由、数据库表结构，必须在 PR 描述里写清楚影响范围。
